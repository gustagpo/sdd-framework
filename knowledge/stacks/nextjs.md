# Lições de Stack — nextjs

> Lições genéricas desta stack aprendidas em rodadas SDD (qualquer projeto). Complementam o perfil `standards/stacks/nextjs.md` — se uma lição contradiz o perfil, corrija o perfil. Cada lição tem 1 linha no `knowledge/INDEX.md`.

### NX-001 — `?redirect=` honrado sem validação é open redirect — e a guarda é por CALL-SITE, não por existir no repo
**Contexto**: fluxos de auth (login, registro, aceite de convite) que honram `?redirect=` pós-sucesso via `useSearchParams()`/`router.push()`.
**Problema**: a guarda (`safeRedirect()` — só caminho interno) existia, tinha testes e estava aplicada no login; o **registro**, adicionado depois, leu o mesmo param cru (`params.get('redirect') ?? '/dashboard'`) — `/register?redirect=https://evil.com` empurra o usuário recém-cadastrado (em contexto de máxima confiança) para fora. É a classe "2º call-site nasce sem a guarda do 1º": a existência da função não protege nada; cada leitura do param é uma superfície nova. Agravante da rodada real: a doc de convenções foi atualizada **afirmando** que registro usava a guarda antes de o código usar.
**Regra**: (1) `router.push`/`redirect()` com valor vindo de query/param **sempre** atravessa a guarda de caminho interno (rejeitar absoluto, `//`, esquema, backslash) — sem exceção por "é só o login"; (2) ao criar a guarda, varrer TODOS os call-sites existentes de leitura do param (grep por `redirect`/`returnTo`/`next`) e deixar a lista no PR — auditoria confere a paridade guarda×call-sites, não a existência da função; (3) doc que declara a guarda cita os call-sites — afirmação genérica ("login e registro usam X") é convite ao drift (ver P-027).
**Origem**: iara, rodada 001-auditoria-fase-0 (12/08/2026) — achado N-1 da revalidação, corrigido como condição do Gate Final; `apps/web/src/lib/redirect.ts` + `register/page.tsx`.

### NX-002 — `beforeSend` do Sentry: `{}` é ENVIADO (só `null` descarta) — e o teste do scrub executa o call-site, não checa o import
**Contexto**: `@sentry/nextjs` (vale para o SDK Node também) com scrub de evento em `beforeSend` nos três configs (client/server/edge).
**Problema**: `beforeSend` que devolve **objeto vazio** faz o SDK enviar um evento sem exception, sem level, sem nada — o descarte só acontece com `null`. Na rodada real o call-site usou a função **errada do módulo certo** (a allowlist de atributos no lugar do scrub de evento): `scrub(<evento>)` → `{}`, e o Sentry do web nasceu **inerte com a suíte verde**, porque o teste só exigia que o arquivo contivesse a string do módulo (`toContain('@iara/telemetry')`) — a paridade de import não prova a chamada certa.
**Regra**: (1) contrato do scrub de evento é explícito: não-normalizável → `null` (descarte), normalizável → evento **utilizável** (`exception`/`stacktrace` preservados, chaves sensíveis e `user`/`cookies`/query fora) — nunca "o objeto que sobrou da filtragem"; (2) o teste **executa** o `beforeSend` exportado de cada config com evento realista e assere as duas direções (preserva exception · remove sensível · lixo → `null`) — nos três configs, porque cada um é um call-site; (3) provar por mutação: trocar a função de volta tem de derrubar teste (na rodada real: 4 caíram).
**Origem**: iara, rodada 002-fundacoes-plataforma (12/08/2026) — BL-1 (QA + Security, convergência independente); fix nos três `sentry.*.config.ts` + `sentry-config.test.ts`.

### NX-003 — O rewrite do Next só PREENCHE `x-forwarded-for` quando ele falta (`??=`, `base-server.js`), não acrescenta o próprio salto: `trust proxy N` chutado entrega ao cliente a escolha do IP que vai para o `audit_log` e para o balde do rate limit — saltos declarados por env com default 0 (peer TCP), e o boot anuncia o modo

**Contexto**: web Next.js fazendo `rewrites()` de `/api/auth` e `/v1` para a API (Express/Nest) atrás de um ALB; `req.ip` alimenta rate limit e coluna `ip` de auditoria; `app.set('trust proxy', 1)` ligado por `NODE_ENV === 'production'`.
**Problema**: o rewrite repassa o header que **recebeu** — se o navegador mandar `X-Forwarded-For: 1.2.3.4`, é isso que chega à API; se não mandar, o Next põe o peer dele. Com `trust proxy 1`, a conta de saltos só fechava por coincidência entre dois comportamentos de terceiros (ALB acrescenta, Next engole); com qualquer N > 0 e o header forjável, o auditado escolhe o IP da própria trilha. E o número certo **não existe** antes de a infra existir.
**Regra**: (1) `trust proxy` sai de uma env (`TRUST_PROXY_HOPS`, inteiro validado) com **default 0** = ignora `X-Forwarded-For`, usa o peer TCP (não forjável) — fail-closed em todo ambiente, inclusive num deploy que esqueça de declarar; (2) o boot emite `http.config { trust_proxy_hops }`: configuração de segurança com default 0 é **visível em quem está rodando**, senão ninguém sabe se a instância está em modo peer ou header; (3) declarar > 0 só quando **todo** salto à frente acrescentar ao header — se a API é alcançada **através** do rewrite, ou `/api/auth` e `/v1` chegam direto do ALB, ou o rewrite passa a acrescentar; decidir a arquitetura **antes** do número; (4) verificação com 2 controles quando a infra nascer: `curl -H 'X-Forwarded-For: 1.2.3.4'` de fora ⇒ trilha e balde mostram o IP real; (5) consequência conhecida do 0 atrás de ALB: balde único de rate limit por task e `ip` = ALB na trilha — débito com gatilho, não melhoria (`actor_user_id` continua a atribuição que vale).
**Origem**: jornada-ticket, rodada 001-eventos-admin (16/09/2026) — S-4 (Security, it.1) → `TRUST_PROXY_HOPS` (Dev Backend), `drafts/EVALUATION.devops.md` §6; `apps/api/CLAUDE.md` §9.

### NX-004 — `next dev` do `pnpm dev` e o webServer do Playwright compartilham `apps/web/.next`: com os dois de pé a suíte INTEIRA cai com a mesma assinatura (`TypeError: a[d] is not a function` no `webpack-runtime`), inclusive casos pré-feature — assinatura uniforme é ambiente, não defeito; e2e com `distDir` próprio

**Contexto**: monorepo com `pnpm dev` (web em :3000) e `pnpm test:e2e` (Playwright sobe api/worker/web em portas próprias, 3100/3101); 4 avaliadores em paralelo na mesma estação.
**Problema**: o build do e2e escreve no mesmo `.next` que o dev server está servindo/observando ⇒ chunks trocados a quente ⇒ 12/12 vermelhos com 30 s de timeout cada, longe da causa. Derrubou a medição de **três** agentes na rodada (DevOps OPS-015, QA, UX/UI) e cada um gastou tempo suspeitando do produto. CI não vê (runner limpo).
**Regra**: (1) o webServer do e2e usa `distDir` próprio (env lida no `next.config`) ou a suíte **verifica** a porta 3000 livre antes de subir e aborta com mensagem clara; (2) diagnóstico: N casos vermelhos com a **mesma** assinatura, incluindo casos que a feature não tocou, é colisão de ambiente (P-028) — não abrir achado de produto antes de reproduzir com a estação parada; (3) o avaliador registra no draft "medido com `.next` limpo e porta 3000 livre".
**Origem**: jornada-ticket, rodada 001-eventos-admin (16/09/2026) — OPS-015 (DevOps it.2), nota do QA no EVALUATION final, `specs/TESTS.md`; débito no STATE.

### NX-005 — Localizadores do Playwright: `getByLabel` casa por TRECHO e `.first()` transforma ambiguidade em alvo errado silencioso; regex de rótulo quebra quando o nome acessível MUDA com o estado; `setInputFiles` fora de `input[type=file]` falha em silêncio; `aria-disabled` não é `disabled` — rótulo exato, sem regex, e o clique inerte assere o que faz

**Contexto**: e2e de formulário com upload (`Enviar imagem` → `Trocar arquivo` → `Trocar imagem`), campos `Cidade`/`Capacidade`, botão "Publicar" com `aria-disabled="true"` e motivo ao lado (o DESIGN exige focável).
**Problema**: `getByLabel('Cidade')` ⇒ 2 elementos (trecho de "Capa**cidade**"); `getByLabel(/imagem|capa/i).first()` ⇒ `<input id="capacity" type="number">`, onde `setInputFiles` não faz nada e o teste falha uma linha depois ("a frase de recusa não apareceu") — a triagem suspeitou do produto; mesmo renomeado o campo, a regex não casaria "Trocar arquivo". `click()` em `aria-disabled` é bloqueado pelo actionability check e parece "tela não respondeu".
**Regra**: (1) localizador é rótulo **exato** (`getByLabel('Vagas', { exact: true })`, `getByLabel('Enviar imagem', { exact: true })`) — nunca regex, nunca `.first()` para calar o modo estrito; nome acessível que muda com o estado é localizado no estado esperado, e a acessibilidade (nome atual) é asserida à parte; (2) entrada de arquivo se assere `toHaveAttribute('type', 'file')` antes do `setInputFiles`; (3) controle `aria-disabled` recebe `click({ force: true })` **e** asserção do efeito do clique inerte (foco vai para a lista de pendências, nada é enviado); (4) rótulo que colide por substring é sinal de vocabulário errado (coluna do banco vazando para a tela) — corrigir o rótulo **e** o localizador, não só um (P-021).
**Origem**: jornada-ticket, rodada 001-eventos-admin (16/09/2026) — O-6/T-1/F-01, aprendizados 2–4 do EVALUATION; `apps/web/e2e/events.spec.ts`; L006 do projeto.

### NX-006 — `scrollWidth − clientWidth = 0` NÃO prova ausência de corte em `input[type=date]`/`select`: o shadow DOM interno não entra na conta (era ali que `0/01/2026` acontecia) — o oráculo é a CAPTURA com o valor lido, e o mínimo intrínseco se mede com clone de mesma fonte

**Contexto**: avaliação de layout (UX/UI, Passo 6) de linha de formulário com controles nativos em grade estreita; asserção "sem corte" por métricas do DOM.
**Problema**: o campo de data reportava `0` de corte enquanto a captura mostrava o mês engolido; a it.2 foi aprovada por métrica e reprovada por olho na it.3. Métrica de largura em controle nativo é oráculo fraco: o conteúdo visível vive num shadow root que `scrollWidth` não vê.
**Regra**: (1) prova de "cabe" em controle nativo é **captura** (por breakpoint) + leitura do valor renderizado; métricas do DOM só como triagem; (2) mínimo intrínseco de `date`/`time`/`select` se mede com um **clone** fora do fluxo, mesma fonte e tamanho (`date` ≈ 152 px, `select` ≈ 148 px em 14 px; sobem com `text-base`), e entra no DESIGN (P-084); (3) largura da trilha real por breakpoint (`col-span-8` de `max-w-6xl` = 689 px em 1440/1280, 603 em 1024) é dado do DESIGN, não descoberta do Passo 6.
**Origem**: jornada-ticket, rodada 001-eventos-admin (16/09/2026) — D-2/S-4 do UX/UI, `EVALUATION.ux-ui.md` §2; conclusão 2 do EVALUATION final.

### NX-007 — Rate limit de auth é orçamento COMPARTILHADO num e2e de um IP só (30/min por IP, stack inteira em 127.0.0.1) e o 429 se disfarça de "a tela de login não respondeu": reusar sessão por papel (`storageState`) em vez de afrouxar o limite — e o `storageState` carrega `session_token` vivo, fica em diretório ignorado desde o 1º dia

**Contexto**: Playwright serial (`workers: 1`, `retries: 0`) contra api com limitador em `/api/auth` (janela fixa de 60 s); login com senha + TOTP em cada teste.
**Problema**: 2 casos do staff caíam com `alert: "Muitas tentativas seguidas…"` — 429 do limitador, não defeito da tela; a tentação é passar um limite frouxo ao webServer do e2e, o que faria uma regressão futura (um `getSession` por navegação) passar no e2e e quebrar em produção. E o `storageState` salvo para reusar sessão contém o cookie de sessão de admin (85 chars) — quase foi commitado (P-085).
**Regra**: (1) o e2e roda o **default de produção** do limitador (é o único lugar onde ele é exercido com o cliente real); (2) sessão por papel é criada uma vez e reusada via `storageState` (login completo só no spec de auth) — a densidade por janela cai de N logins para 2 fluxos por arquivo; (3) a validação de sessão por navegação (`/v1/me`) fica **fora** do prefixo limitado; (4) `storageState` vive em caminho já no `.gitignore` (par de trace/vídeo), nunca em scratch improvisado; (5) 429 no e2e se reconhece pela frase do limitador no `alert` — não abrir achado de tela.
**Origem**: jornada-ticket, rodada 001-eventos-admin (16/09/2026) — T-3 (QA), Q-3 (DevOps §7), Q-6; `specs/TESTS.md` do projeto.
