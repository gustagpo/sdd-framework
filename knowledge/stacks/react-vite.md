# Lições de Stack — React + Vite

> Lições genéricas desta stack (React 18 + Vite + TS) aprendidas em rodadas SDD (qualquer projeto). Complementam o perfil `standards/stacks/react-vite.md` — se uma lição contradiz o perfil, corrija o perfil. Cada lição tem 1 linha no `knowledge/INDEX.md`.

### R-001 — Flag de feedback visual transitório com `setTimeout` não pode servir de flag de permissão de fluxo
**Contexto**: um componente que dá feedback efêmero a uma ação (o "Copiado ✓" que aparece por 2 s e volta a "Copiar") e, no mesmo componente, controla se o usuário **já pode avançar** (habilitar "Concluir", liberar ESC/clique-fora num dialog anti-perda).
**Problema**: reusar uma **única** variável (ex.: `copiado`, resetada por `setTimeout(...2000)`) para as duas coisas acopla um estado **transitório** a uma decisão **permanente**. Efeito real observado: o botão "Concluir" habilitava ao copiar e **voltava a desabilitar 2 s depois**; o dialog re-bloqueava a saída de quem já havia copiado. Um clone de página-modelo herda esse padrão sem perceber.
**Regra**: separe sempre **dois** estados — o permanente ("já cumpriu o passo": `jaCopiou`/`confirmou`, nunca resetado por timer) e o transitório ("mostrando o feedback": `mostrandoCheck`, esse sim com `setTimeout`). A permissão de fluxo (`podeConcluir`, `bloquearSaida`) deriva **só** do permanente. O `setTimeout` toca **apenas** o feedback visual (ícone + `aria-live`), nunca a habilitação de controles.
**Origem**: algar/EVALUATION UX#1/R-01 da rodada bypass-seguranca-integrador (22/07/2026)

### R-002 — Estado vazio que AFIRMA algo não pode ser o fallback de dado ausente: distinguir `undefined` (não veio) de `[]` (não há)
**Contexto**: componente que renderiza uma lista opcional vinda da API (`campo?: T[]`) e cujo estado vazio tem **significado afirmativo** no design ("sem bônus", "sem pendências", "nenhum débito") — não é mera omissão visual.
**Problema**: o padrão reflexo `Array.isArray(x) ? x : []` colapsa dois casos semânticos distintos: `[]` ("li o dado; não há") e `undefined` ("o dado **não veio**" — gate de feature OFF, degradação por falha, backend que ainda não implementa o campo). O componente então **afirma** o estado vazio sobre dado que ninguém leu — em rodada real, a coluna disse "sem bônus" para linhas com bônus durante toda a janela em que o campo não existia/estava gateado, sem nenhum erro visível (a ausência de campo opcional é silenciosa em TypeScript).
**Regra**: quando o estado vazio **afirma** (e não apenas omite), a renderização trata `x == null` como "sem informação" (célula vazia, `—` neutro com tooltip, ou skeleton) e reserva a afirmação ("sem X") para `x.length === 0` real. O contrato com o backend acompanha: degradação por falha **omite o campo** (nunca devolve `[]`/valor neutro fabricado) — a distinção só funciona se os dois lados a honrarem.
**Origem**: algar/LESSONS.md L085 — achados Q-8/Q-9 da rodada servico-bonus-temporario (28/07/2026).

### R-003 — Campo **não-opcional** vindo de API é promessa, não garantia: normalizar no serviço, com defesa também no componente
**Contexto**: tipo TS do front declarado a partir do contrato (`acoes: Acao[]`, `trilha: Evento[]`) e componente que consome direto (`data.acoes.length`, `data.acoes.map(...)`).
**Problema**: o tipo do front é uma **declaração de intenção sobre dado de terceiro** — o compilador aceita `acoes: Acao[]` e o runtime recebe `undefined` porque o backend (implementado em paralelo) projetou outro nome, ou porque a degradação omitiu o campo. O resultado é `TypeError: Cannot read properties of undefined` na tela inteira — falha **dura**, não graciosa. Em rodada real, dois endpoints do mesmo contrato quebraram assim (drill-down de execução e log de notificações), e o tipo "correto" foi justamente o que deu a falsa sensação de segurança.
**Regra**: (1) o tipo do front declara coleções vindas de API como **opcionais** (`acoes?: Acao[]`) — a honestidade do tipo é o que força o tratamento; (2) a normalização acontece **uma vez, no serviço** (função pura testável: `?? []`, tolerância a alias de campo durante a transição, conversões de forma), nunca espalhada por componente; (3) o componente ainda assim usa `?? []` no ponto de uso — **defesa em profundidade**, porque nem todo caminho passa pelo serviço (cache, props, testes); (4) atenção: `?? []` para coleção cujo vazio **afirma** algo ("sem pendências") colide com R-002 — quando o vazio é afirmativo, distinga `undefined` de `[]` em vez de colapsar.
**Origem**: algar/LESSONS.md L091 — BLOQ-4/BLOQ-5 da rodada esteira-cobranca-inadimplencia (31/07/2026); fix com `lib/esteiraNormalizar.ts` (puro, testado com fixture do produtor) plugado no serviço + `?? []` nos componentes.

### R-004 — "Carregando" não é "indisponível": catálogo remoto ainda em voo renderizado como falha treina o operador a ignorar alerta

**Contexto**: tela de cadastro cujo formulário depende de um **catálogo vindo da API** (lista de variáveis/opções permitidas) para rotular o que o usuário escolheu; enquanto o catálogo não chega, os rótulos não existem.
**Problema**: o reflexo é `catalogo.length === 0 ⇒ estado de falha` ("Não foi possível carregar os dados") — que aparece em **todo** primeiro render, antes de qualquer erro. O operador vê um alerta âmbar por 300 ms sempre que abre a tela, aprende que o alerta não significa nada, e **o alerta de falha real deixa de ser lido**. Pior: a mesma condição desabilita controles, então o usuário atribui a lentidão a um erro que não houve.
**Regra**: (1) derive um estado com **três** valores numa função **pura e testável** (`carregado | carregando | indisponivel`) a partir de `(dados, carregando)` — catálogo presente com refetch em curso continua `carregado`; (2) o alerta de falha fica **atrás do gate `indisponivel`**; o estado de carga tem placeholder/linha neutra própria ("Carregando dados…") e texto acessível diferente ("carregando os nomes", não "dado não identificado"); (3) o que já é verdade sem o catálogo (a **ordem** das posições, os índices) continua sendo mostrado — degradar não é apagar; (4) sem jsdom, o teste é da função pura (3 estados × combinações) + guarda **estrutural** de que o âmbar está dentro do gate de falha.
**Origem**: algar, rodada notificacao-cobranca-whatsapp-hsm (19/08/2026) — achado U-1 do UX/UI (`MapaPosicoes.tsx`), corrigido com `estadoCatalogo()` puro e provado por mutação.

### R-005 — Foco programático após mover/remover item: sem `id` no alvo o `focus()` é no-op silencioso, e alvo `disabled` engole o foco

**Contexto**: lista editável (posições de um mapa, linhas de um formulário) com botões ↑/↓/remover; ao mover ou remover, o React remonta as linhas e o foco volta para o `<body>` — quem navega por teclado se perde no topo da página.
**Problema**: a correção natural (`document.getElementById(idDoBotao)?.focus()`) é **silenciosamente inútil** em dois casos que a revisão não vê: (1) os botões renderizados não têm `id` — `getElementById` devolve `null` e o `?.` engole tudo; (2) o alvo escolhido está `disabled` (o `Select` da linha fica travado quando o catálogo remoto não carregou), e `focus()` em elemento desabilitado não faz nada. Nos dois casos o teste "chamou `focus`" passa e o usuário continua perdido.
**Regra**: (1) a **decisão** de para onde vai o foco é uma função **pura** (`focoAposMover`/`focoAposRemover`) que recebe índice, tamanho da lista e direção e devolve o id do alvo — testável sem DOM, incl. os casos de ponta (primeira/última linha, lista de 1, lista esvaziada ⇒ botão "adicionar"); (2) **todo** alvo possível ganha `id` explícito e estável no JSX, com guarda estrutural de que o `id` existe; (3) a aplicação do foco percorre uma **cadeia de fallback** que pula alvo ausente ou `disabled`; (4) o efeito real (foco visível, `aria-live` anunciado, ordem de tabulação) **não é testável sem jsdom** — declare-o no roteiro **manual** do Passo 6 em vez de fingir cobertura.
**Origem**: algar, rodada notificacao-cobranca-whatsapp-hsm (19/08/2026) — achado U-2 do UX/UI; 9 testes puros + 3 estruturais, com o foco real remetido ao roteiro de staging.

### R-006 — Cliente que corta a lista em N pede N+1 (sentinela) ou usa o `total` — senão o detector de truncagem é inalcançável e o corte é silencioso

**Contexto**: tela que mescla/exibe listas de múltiplas origens com teto client-side ("as 100 mais recentes por origem") e aviso de truncagem ("exibindo as N mais recentes").
**Problema**: o hook pedia `pageSize: TETO` à API e a função de mescla marcava `truncado` quando recebia **mais** que o teto — condição **inalcançável por construção**: a API nunca devolve mais do que se pediu. O aviso de truncagem existia, tinha teste (da função pura, que passava com input sintético) e **nunca apareceria** em produção; o usuário veria "100 notas" como se fossem todas. A revisão não pega porque cada metade (pedido e corte) está certa isoladamente.
**Regra**: (1) quem corta em N pede **N+1** — o item excedente é sentinela que prova "há mais", e o corte continua em N; alternativa igualmente válida: comparar com o `total` da resposta paginada quando a API o devolve; (2) o teste assere **o que o hook pede à API** (o `pageSize` real da chamada), não só a função pura de corte — senão a inconsistência pedido×corte fica entre dois testes verdes; (3) truncar nunca é silencioso: teto novo no cliente nasce com o caso "N+1 itens ⇒ aviso visível".
**Origem**: algar, rodada dashboard-360-contrato-clausula (19/08/2026) — bloqueante 2 da it.1 (C-14, `useNotasContrato`/`mesclarNotas`), corrigido e provado por mutação (M5: voltar `pageSize: TETO` ⇒ vermelho).

### R-007 — React Query: `QueryClient` sem `defaultOptions` refaz a chamada em foco/mount/reconnect — query de integração PAGA usa constante anti-refetch compartilhada, assertada POR hook

**Contexto**: app com `QueryClient` criado sem `defaultOptions` (default do React Query: `refetchOnWindowFocus`/`refetchOnMount`/`refetchOnReconnect` = `true`, com retries) e queries que disparam chamada **paga** ou com custo por requisição (proxy para operadora, API por consulta).
**Problema**: o default transforma "montei o card e troquei de janela" em **chamadas pagas automáticas** — invisível em dev (a tela "só atualiza") e caro em produção; numa rodada real um hook de consulta à operadora já estava **em produção** com esse defeito antes de a regra "1 clique = 1 chamada" ser formalizada. Corrigir o `QueryClient` global não é opção barata em app maduro (muda o comportamento de dezenas de telas de dado local — regressão fora de escopo).
**Regra**: (1) toda query de integração paga espalha uma **constante compartilhada** (`OPCOES_ALGAR`-like: `enabled: false` ou gated por clique, `retry: false`, `refetchOnWindowFocus/Mount/Reconnect: false`, sem `refetchInterval`) — nunca opções repetidas à mão por hook; (2) o teste assere a constante **em cada hook** que a espalha (recorte por símbolo — ver `jest.md` J-007): asserção no arquivo inteiro deixa um hook sem o spread com a suíte verde; (3) o invariante de UI correspondente ("0 chamadas ao service até o clique") ganha caso próprio; (4) ao introduzir a regra, fazer o **grep dos hooks existentes** da mesma integração — o defeito costuma já estar em produção.
**Origem**: algar, rodada dashboard-360-contrato-clausula (19/08/2026) — C-02 do CONTRACT (`lib/algarQuery.ts`), correção de carona do `useEstadoAlgar` pré-existente, provado por mutação (M1/M1b).

### R-008 — Foco pós-ação cobre o desmonte do CONTAINER, não só do controle: toda ação que pode remover a própria seção declara um alvo de fallback FORA dela (nunca `<body>`)

**Contexto**: card/seção com ação (botão "Sincronizar", "Remover", "Aplicar") cujo desfecho pode (a) trocar o botão por outro estado, (b) desligar o botão (flag/permissão) ou (c) **desmontar o card inteiro** (a entidade deixou de se aplicar); função pura decide o alvo de foco pós-ação (R-005) e o teste cobre (a) e (b).
**Problema**: o alvo de foco (`#skeelo-titulo` com `tabIndex={-1}`) mora **dentro** do card; no desfecho (c) o card sai do DOM junto com o alvo, o `focus()` é no-op e o foco cai no `<body>` — leitor de tela perde o contexto e o teclado volta ao topo da página; o toast ainda anuncia, mas a navegação quebrou. O DESIGN tratou o foco como propriedade do **controle** (E7: botão some ⇒ foca o título) e não da **seção**; o cenário é raro e só apareceu na avaliação de a11y.
**Regra**: (1) a matriz de estados do DESIGN lista, por desfecho, o alvo de foco — e todo desfecho que pode remover a seção aponta para uma **âncora estável da página** fora do card (heading da página/da aba com `tabIndex={-1}`), nunca `<body>`; (2) a função pura recebe o estado **depois** da ação e devolve `alvo | null` com um alvo pinado por desfecho (botão vivo → botão · flag OFF → título do card · card desmontado → âncora da página); (3) o CONTRACT ganha o caso puro por desfecho e o roteiro manual a alínea "foco após o card sumir"; (4) `sonner`/live region anuncia o resultado independentemente — anúncio não substitui foco.
**Origem**: algar, rodada skeelo-ativacao-clientes (25/08/2026) — débito U-2 do EVALUATION (UX/UI), `alvoFocoPosSincronizacao` cobre só o desmonte do botão; regra proposta para a próxima rodada de DESIGN (F-011 / F-045f).

**Reforço (26/08/2026, algar, integracao-stations-superapp)**: 2ª implementação já a partir do DESIGN — `alvoFocoPosSincronizacao` devolve `#stations-titulo` quando só o botão desmonta e `#linha-titulo` (âncora da página, `tabIndex={-1}` no `<h1>`) quando o card inteiro desmonta; a região `role="status"` é limpa por `setTimeout` (10 s, deliberadamente > 4 s do toast) com `clearTimeout` no `useEffect`, e o hook fica **antes** do `return null` do estado "não aplicável" (ordem de hooks) — M-06 do EVALUATION.

**Reforço (16/09/2026, jornada-ticket, 001-eventos-admin — F-03/D-1, 3ª ocorrência da classe)**: painel de publicação com confirmação inline caiu no `<body>` 3× porque o bloco de botões era desmontado e o gatilho guardado deixava de existir. Fechado com `alvosDeRetorno`: "Voltar"/`Esc` ⇒ gatilho; desfecho que desmonta o gatilho ⇒ `#titulo-secao-publicacao` (`<h2 tabIndex={-1}>`). Dois acréscimos à regra: (a) **medição vence declaração** — o dev contou 11 transições (8 voltas + 3 desfechos); o UX/UI mediu Voltar **e** Esc nas 5 ações e 4 desfechos = **14** (`reopen` também desmonta o próprio botão), lendo o foco **um frame depois** (2× `requestAnimationFrame` — no mesmo frame devolve `<body>` e reprova código certo); (b) destino de foco programático usa `focus:` (não `focus-visible:`, que apaga o anel quando o desfecho é disparado por mouse — o único momento em que a tela move o foco sozinha); controle alcançado pelo teclado usa `focus-visible:`. Comentário que descrevia a **intenção** ("devolve o foco ao gatilho") enquanto o código caía no `<body>` foi reescrito para descrever o comportamento — comentário de intenção é pior que nenhum (J-005/P-037).

### R-009 — Duas superfícies (título e corpo, badge e ação) derivadas do MESMO estado por normalizações diferentes se contradizem: uma função pura decide as duas, e o teste assere a coerência entre elas

**Contexto**: card/faixa cujo **título** ("Assine seu contrato" / "Contrato assinado") e **corpo/CTA** derivam do estado de um recurso remoto (`documento.estado`), com regra de normalização (`trim().toUpperCase()`, estado ausente/desconhecido ⇒ neutro).
**Problema**: o título era decidido inline no componente com comparação crua e o corpo por uma função pura normalizada ⇒ para `"assinado"` (minúsculo) ou estado desconhecido, o título afirmava uma coisa e o corpo mostrava outra (U-01, 🟠). O teste de cada metade passava; a **coerência** entre elas não era asserida por ninguém.
**Regra**: (1) toda derivação de UI a partir do mesmo estado sai de **uma** função pura (`{titulo, corpo, cta, tier}` = f(estado normalizado)) e o componente só renderiza; (2) o teste tem casos de **coerência** (título e corpo do mesmo `estado` nunca se contradizem) sobre a tabela de estados **incluindo** caixa/espaços/ausente/desconhecido; (3) ação indisponível é **ausente** (nunca `disabled`) e `aria-label` de ação aparece **uma** vez — `map` de ações em pontos mutuamente exclusivos (U-04/U-07); (4) o tier de **diagnóstico** (motivo de falha) e o tier **visual** (cor) são funções separadas — não reutilizar a mesma tabela para os dois; (5) valor-credencial (link de assinatura) é buscado no clique (`fetchQuery`, `gcTime: 0`) e vai direto ao clipboard — nunca em DOM, estado, cache ou log.
**Origem**: algar, rodada integracao-d4sign (27/08/2026) — U-01/U-04/U-07 (UX/UI, it.1), `lib/assinaturaContrato.ts:147,633-646` + `assinaturaContratoCorrecoes.test.ts` (22 testes com `lerObrigatorio`).

**Reforço (27/08/2026, algar, ciclo-vida-contratual — F-2 🔴)**: mesma classe num **número**, não num estado textual — `dias_restantes === 0` produzia "Vence hoje" na linha do card (função A) e "Vence em **0 dias**" no alerta âmbar do mesmo card (função B), com o DESIGN proibindo "0 dias" na tela. A regra (1) vale para toda copy derivada do mesmo valor (linha, alerta, toast, badge): uma função decide, e o teste varre **estados × valores** provando que a substring proibida (`0 dia(s)`) não sai de **nenhuma** peça — com controle do próprio regex (F-1/F-2 → +20 testes). Companheira: botão que abre dialog dependente de dado em voo **some** enquanto carrega (F-3) — "Prazo indeterminado" só com o dado carregado e ausente (R-002/R-004).

### R-010 — Copy de erro que ENUMERA causas se confere contra o conjunto FECHADO de causas do backend (faltava justamente a mais provável em produção); dica/tooltip com trigger não focável é inalcançável por teclado — `tabIndex={0}`/`<button>` + `aria-describedby`

**Contexto**: card de estado com copy única para um slug de erro (`SEM_CONFIGURACAO`) que no backend tem N causas (`MINUTA_AUSENTE | MINUTA_AMBIGUA | TEMPLATE_UUID_AUSENTE | mapa sem placeholder válido`), e badge de diagnóstico com tooltip explicativo cujo trigger é um `<span>`.
**Problema**: a copy listava 3 das 4 causas — faltava `MINUTA_AUSENTE`, que era o estado de **4 dos 5 tipos** no dia 1 (a causa mais comum em produção era a única sem texto); e o tooltip só abria com mouse. Os testes de função pura asseriam **texto**, não **cobertura**, e o `vitest` em `environment: node` não exercita foco.
**Regra**: (1) quando a copy enumera causas, o teste itera o **conjunto exportado** pelo backend (ou constante espelhada com teste de paridade) e assere que cada causa aparece na copy — é teste de cobertura causa×copy, não de string; a causa mais frequente (medida no banco) vem **primeiro**; (2) trigger de tooltip/dica é elemento focável (`<button type="button">` ou `tabIndex={0}`) com `aria-describedby`; roteiro manual de a11y não substitui a asserção estrutural (`grep`/render) quando o ambiente de teste é `node`; (3) UX/UI confere no Passo 6 a copy contra a lista de slugs/causas do CONTRACT, não contra o DESIGN.
**Origem**: algar, rodada cadastro-minutas-documento-aceite (28/08/2026) — D-1/D-2 do UX/UI (it.1 🔴 → it.2 ✅ por mutação); L199 do projeto.


### R-011 — N botões que compartilham UM estado "em voo" (`emVoo: boolean`) mostram o rótulo de carregamento no botão ERRADO: o estado guarda QUAL ação está em voo, e uma função pura devolve o rótulo só quando `acaoEmVoo === acaoDoBotao` (os demais ficam `disabled`, sem rótulo)

**Contexto**: card com 3 ações mutuamente exclusivas (Autorizar · Concluir · Cancelar) e um único `isPending` derivado dos hooks; rótulo "Enviando…" aplicado a todo botão com `disabled={emVoo}`.
**Problema**: clicar "Cancelar" fazia "Autorizar" exibir "Enviando…" (e vice-versa) — o usuário lê que a ação errada está em curso; o teste de estrutura só conferia `disabled`, não o rótulo por botão.
**Regra**: (1) estado `acaoEmVoo: 'autorizar' | 'concluir' | 'cancelar' | null` (derivado dos hooks, puro), nunca booleano compartilhado; (2) `rotuloBotao(acaoDoBotao, acaoEmVoo)` é função pura exportada e testada com a matriz ações × em-voo (o rótulo de voo aparece em exatamente 1 célula por linha); (3) `disabled` continua para todos enquanto algo está em voo, e o `role="status"` anuncia **qual** ação; (4) mutante: trocar a comparação por `!!acaoEmVoo` ⇒ vermelho (aqui 2 ❌); irmã de R-009 (duas superfícies derivadas do mesmo estado por normalizações diferentes).
**Origem**: algar, rodada paypal-autorizacao-vault-portal (10/09/2026) — 🟡 3 do UX/UI (it.1) → R-16 (`pagamentoAutomaticoPortal.ts` `rotuloBotaoPagamentoAutomatico`, `PagamentoAutomaticoTab.tsx`), aprovado na it.2.

### R-012 — Parser por TIPO de campo em pt-BR: dinheiro aceita `,` ou `.` como decimal; QUANTIDADE usa `.` como milhar — "10.000" lido como 10 é cobrança 1 000× indevida; entrada ambígua é erro de validação, nunca número silencioso

**Contexto**: formulários com valores monetários (`parseDecimalBR`) e, na mesma rodada, campos de franquia/bloco/quantidade em unidades (mensagens, tokens); o helper de dinheiro foi reaproveitado.
**Problema**: `parseDecimalBR("10.000")` = 10 e `"1.000"` (o exemplo da própria doc do helper) = 1; a prévia viva ecoava o valor errado sem aviso e a validação aceitava.
**Regra**: (1) o DESIGN declara o formato de entrada **por tipo de campo** (dinheiro × quantidade × percentual) e o CONTRACT um parser por tipo; (2) `parseQuantidadeBR`: `.` só como separador de milhar em grupos de 3, decimal só com `,`, inteiro quando o campo é bloco (≥ 1), qualquer forma ambígua (`"10.00"`, `"1.0000"`) ⇒ erro de validação; (3) vetores em **cada call-site** (`"10.000"→10000`, `"1.000"→1000`, `"1.234,5"→1234,5`, `"1,5"→1,5`, `"10.00"`⇒erro) + grep-guard "quantidade nunca passa por `parseDecimalBR`" + mutante "volta ao parser de dinheiro" vermelho; (4) a prévia ecoa o valor parseado formatado (`10.000`) para o usuário conferir.
**Origem**: algar, rodada faturamento-consumo-fundacao (22/09/2026) — E-001 (bloqueante do UX/UI), `lib/consumoMedido.ts:47-92`, `consumoMedidoCorrecoes.test.ts`; L233 do projeto.

### R-013 — Diálogo que executa ação irreversível em SÉRIE bloqueia `onOpenChange`, `onEscapeKeyDown` e `onInteractOutside` e esconde o X enquanto a série voa (Cancelar `disabled` não basta); ação sem permissão/gate/config é botão AUSENTE, nunca `disabled`

**Contexto**: "Fechar em massa" (N fechamentos sequenciais, cada um emite fatura + cobrança + e-mail) num `Dialog` do Radix/shadcn; botões condicionados a permissão RBAC e a gate de parâmetro.
**Problema**: ESC/clique fora/X fechavam o diálogo com a série ainda em voo — o usuário lia "cancelei", mas os fechamentos continuavam sendo emitidos; o teste só cobria o botão Cancelar.
**Regra**: (1) estado `emVoo` bloqueia `onOpenChange(false)`, `onEscapeKeyDown`/`onInteractOutside` com `preventDefault`, e o X é omitido (não `disabled`) — helper único (`protecaoDialogoEmVoo`) reusado por todo diálogo de ação em série, desligado no `finally`; (2) "Parar depois deste" é a única saída antecipada, e para entre itens; (3) teste: em voo, ESC/overlay/X não fecham; mutante "sem guarda" vermelho; (4) botão de ação que o usuário não pode/há gate OFF é **ausente** do DOM (`temPermissao && gate ? <Button/> : null`), nunca `disabled` — `disabled` promete que "vai ficar disponível" e vaza a existência da ação.
**Origem**: algar, rodada faturamento-consumo-fundacao (22/09/2026) — E-006 (`FecharFechamentoDialog.tsx`, `UploadLoteDialog` como molde), grep `disabled={!pode…}` = 0; convenção do projeto (Skeelo/Stations/PayPal).

### R-014 — "Chave ausente" tem UM significado por projeção: campo derivado que o motor grava sempre (`blocos`) não serve de indicador de presença (`!= null`), e quando o backend omite um campo PORQUE o caso é ambíguo o front "não afirma" — decisão por função pura, testada nos 4 casos, com mutante `!= null`

**Contexto**: convenção "ausência ≠ zero" (campo opcional não resolvível é omitido); apuração com `blocos` (sempre gravado) e `bloco_cobranca` (omitido quando inequívoco não é possível); tabela decidia "serviço por bloco?" por `a.blocos != null`.
**Problema**: serviço cobrado por mensagem aparecia como "2.000 blocos"/"por bloco"; a 3ª correção (E-017 → E-038 → E-040) só fechou quando a decisão saiu de um campo derivado e foi para uma função pura com os casos enumerados (unidade / bloco com tamanho / bloco sem tamanho / ambíguo).
**Regra**: (1) o CONTRACT declara, por projeção, o que a ausência de cada chave significa (e o backend só omite com esse significado); (2) o front nunca infere presença por campo que o motor preenche sempre — usa a chave semântica (`bloco_cobranca`) ou uma função pura (`porBlocoDaApuracao`) exportada e testada; (3) caso ambíguo ⇒ não afirma unidade nem sub-linha; (4) mutante: trocar a função por `campo != null` deixa ≥ 1 vetor vermelho; (5) front e back sobem juntos quando a semântica de ausência muda (condição de go-live nominal).
**Origem**: algar, rodada faturamento-consumo-fundacao (22/09/2026) — E-016/E-038/E-040, A-13/D-it2-1, `lib/consumoMedido.ts:1093-1113`, `consumoMedidoBlocoApuracao.test.ts`; Aprendizado 13.

### R-015 — Download cross-origin por `fetch`: o navegador NÃO expõe `Content-Disposition` sem `Access-Control-Expose-Headers` — o nome do arquivo é fallback DETERMINÍSTICO igual nos 2 lados, o Blob sai por `<a download>` e HTML de terceiro com PII nunca é renderizado na origem do app

**Contexto**: SPA em origem diferente da API; rota autenticada que devolve um documento HTML de terceiro (`attachment; filename="declaracao-conteudo-<objeto>.html"`); o DESIGN pedia "ler o `Content-Disposition`"; o serviço HTTP do projeto é `fetch` (sem interceptor que force JSON).
**Problema**: sem `Access-Control-Expose-Headers: Content-Disposition` no CORS, `res.headers.get('Content-Disposition')` é `null` no navegador (o header existe — `curl`/borda o veem) ⇒ o nome do download cairia num genérico; mudar o CORS estava fora do escopo. Segundo risco: abrir o HTML numa aba/`iframe`/`dangerouslySetInnerHTML` executa markup de terceiro na origem do app.
**Regra**: (1) nome de arquivo por função pura com fallback determinístico (`declaracao-conteudo-<codigo>.html` / `…-entrega-<id>.html`), **idêntico** ao que o backend envia (teste de paridade nos 2 lados; o backend continua enviando o header para clientes que o leem, e o filename só aceita o formato do código — CR/LF/aspas nunca chegam ao header); (2) `fetch` cru → `Blob` **`application/octet-stream`** (nunca `text/html`) → `URL.createObjectURL` → `<a download>` → `revokeObjectURL` no `finally`; (3) `code` do erro preservado lendo o corpo como texto→JSON antes de decidir blob; (4) grep-guard nos arquivos novos: 0 `window.open`, 0 `iframe`, 0 `dangerouslySetInnerHTML`; (5) o CONTRACT registra "CORS não muda; fallback é o caminho efetivo" como conflito resolvido (DESIGN × Front/Security), não como surpresa do Passo 6; (6) botão de download ausente (não `disabled`) sem permissão/gate, em voo por botão (R-011).
**Origem**: algar, rodada correios-etiqueta-validade-e-dce (22/09/2026) — C-4/C-5 do CONTRACT, S-01/S-03 do Security, F-909, `correiosService.ts` (`nomeDoDownloadDce`, `baixarDce`); L245 do projeto.
